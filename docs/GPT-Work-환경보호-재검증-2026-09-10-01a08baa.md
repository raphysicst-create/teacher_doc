## 6. 원인 조사

확인된 사실:

- 신뢰 데이터는 현재 사용자 config.toml의 hooks.state에 저장돼 있고 정의 해시가 맞다. 이제 “아직 untrusted”가 원인이라고 설명할 수 없다.
- 동일 설치 엔진의 새 프로세스는 hooks=true·trusted를 읽는다.
- Work 앱 엔진 PID 12008은 **20:28:43 KST**부터 계속 실행 중이다.
- 이번 작업은 **23:13:29 KST**에 시작된 기존 세션이다.
- 사용자 신뢰 설정 파일의 수정 시각은 **23:38:32 KST**다.
- 이번 턴 호스트 로그는 local 환경과 **config: FromThread**를 기록했다.
- 실제 호출은 code mode 안의 하위 도구 경로를 사용했다.
- 직전 40분의 실제 hook 계열 로그 target 조회에서는 0건이었다. 사용자 메시지·도구 명령에 들어간 “hook” 문자열은 실행 로그로 세지 않았다.

남은 원인 후보:

1. **기존 세션에 남아 있는 설정·훅 상태:** 신뢰 변경 전에 시작한 작업이 FromThread 설정을 사용한다는 관측과 부합한다. 다만 활성 세션의 내부 hook manager를 직접 조회하지 못했으므로 캐시 문제로 확정하지 않는다.
2. **code mode 내부 호출의 훅 전달 경로:** 상위 functions.exec와 하위 tools.* 사이에서 이벤트가 전달되는지 미확인이다. 새로 시작한 세션에서도 실패하는지 구분해야 한다.
3. **등록 훅의 실행 오류:** 실제 호출 이벤트와 stderr가 없어 확정·배제할 수 없다. 직접 스크립트 성공으로 앱 경로를 대체해 진단하지 않았다.

**단순 matcher 이름 차이는 원인으로 확정하지 않는다.** 공식 문서는 exec_command가 Bash로 매칭되고 apply_patch·MCP도 훅 대상이라고 명시한다. 특수 경로는 제외될 수 있다는 제한도 있어, 현재 내부 경로는 실측이 필요하다. [OpenAI 공식 훅 도구 적용 범위](https://learn.chatgpt.com/docs/hooks#tool-coverage)

설정·코드 수정, 앱 강제 종료, 신뢰 재설정으로 원인 관측을 흐리지 않았다. [프로세스 관측값](../.claude/scratchpad/work-retest-20260910-01a08baa/runtime-observed.json), [실행 로그 조회 범위](../.claude/scratchpad/work-retest-20260910-01a08baa/hook-runtime-log-observation.json).

다음 사용자 조작은 신뢰 재승인이 아니다.

1. 이 답변이 끝난 뒤 같은 대화에서 **“이번 답변의 종료 훅 결과를 확인해줘”**라고 요청하면 저장한 사전 상태와 비교할 수 있다. 먼저 이 증거를 확인하면 현재 세션의 Stop 결과와 재시작 이후 결과가 섞이지 않는다.
2. 그 다음 Work 앱을 정상 종료하고 다시 열어 이 프로젝트의 로컬 작업을 시작한다. 다른 작업이 진행 중이면 종료 시점을 사용자가 정한다. 앱 전체를 새로 띄운 뒤에도 실패하면 기존 세션 상태만의 문제라는 가설은 약해진다.
3. 재시작 후에는 먼저 보호 파일 수정 1건과 허용 생성·감사 기록을 확인한다. 실제 사전 deny와 원본 불변이 확인되면 나머지 보호 경로·Stop 실패 자극을 이어 확인한다. 단순 trusted/Active 표시로 넘어가지 않는다.
