# 남은 시험 실행 결과 — 2026. 9. 13.

Hwp_doc에서 렌더 오탐을 수정하고 실제 훅·등록 준비·전달 실패 처리를 시험했다. **전체 업무 인수와 정식 배포는 완료하지 않았다.** 새 등록/문안 확인, Codex CLI의 한글 실행 환경 문제, 배포 권리 확인이 남아 있다.

기존 세션의 미커밋 변경을 보존했다. 이번 운영 코드 변경은 `scripts/render_check.py`, 추가 회귀시험은 `tests/test_render_check.py`다. 회귀시험 **103개 통과**, 운영 knowledge/output/기존 승인 등록 파일 **460개 해시 불변**을 확인했다. 실무 원본에 쓰기 시험을 하지 않았다. 최초 독립 평가의 판정표를 이번 구현자 후속 결과로 덮어쓰지 않았다.

## 실행 환경과 해석

- 실제 Claude Code CLI: 2.1.211, 기본 모델 claude-sonnet-5. 프로젝트 훅을 로드하고 실제 Write/Edit/Bash/MCP/Stop 이벤트를 관측했다.
- 실제 Codex 앱 번들 CLI: 0.153.4, 기본 모델 gpt-6-astra, workspace-write. 일반 메뉴의 프로젝트 신뢰와 `/hooks` 검토를 사용했다. 우회 플래그·시스템 실행 정책 변경·앱 업데이트는 하지 않았다.
- 현재 Codex Desktop 세션: 도구 실행으로 같은 코드·Python312·시험 작업을 호출했다. 이 환경의 성공을 별도 CLI 환경의 성공으로 바꾸지 않았다.
- COM은 순서대로 실행했다. 코드·시험 기록은 `tmp/remaining-20260913/`에 있으며, 실제 OneDrive 대신 각 시험 폴더의 `fake-copy/`를 사용했다. 시험 문서를 실제 업무 검토 로그에 넣거나 발송하지 않았다.

Codex의 최초 무표시 CLI 호출은 아직 훅을 신뢰하지 않은 상태였으므로 최종 근거는 별도의 `codex-plain-trusted` 호출이다. 정상 `/hooks` 메뉴에서 PreToolUse/PostToolUse/Stop 각각 Active=1을 확인했다. [공식 훅 문서](https://learn.chatgpt.com/docs/hooks)의 신뢰 구분과 실제 관측을 함께 기록했다.

Claude MCP 첫 시험은 모델이 사용자 허용보다 로컬 지침을 우선한다고 잘못 해석하여 두 덮어쓰기 호출을 생략했다. 정상 새 출력 패치는 첫 시도 0개 적용, 두 번째 1개 적용/미적용 잔차가 있었고 전체 호스트가 360초 제한에 걸렸다. 이를 보호 성공으로 채점하지 않았다. 두 번째 좁힌 시험에서 두 차단 호출을 확인했다. 첫 기록은 보존했다.

Claude 미신뢰 UI 첫 시도는 입력 타이밍으로 신뢰 선택이 수리되어 거부 근거가 되지 못했다. 문서 도구 호출 없이 종료했다. 별도 새 시험 폴더에서 `No, exit`를 관측·확정한 두 번째 결과만 거부 근거로 사용했다. 시험 폴더 준비 중 동적 PowerShell 쓰기 한 건은 정적 경로 구분 불가로 훅에 차단됐으며, 새 파일 생성과 단일 리터럴 복사 명령으로 준비했다.

## 등록·W1·W2·전달

양식 `trial-gianmun/1`을 Claude 실제 도구와 현재 Codex Desktop 도구에서 각각 원본 가져오기 → 실제 슬롯 매핑 → 구조 → 네임스페이스 → finalize → layout → 프로파일 → 한글 실열림 → PDF → PNG까지 준비했다. **각 8단계 pass, 등록은 awaiting_review**다. 원본과 template.hwpx 해시는 두 환경 모두 동일하며, 두 PNG도 해시가 같다. Codex가 PNG를 직접 읽어 제목·본문 문단·여백 배치를 확인했다. 사람 판독이나 등록 승인을 만들지는 않았다.

이번 등록은 일반 W1·W2 기안문용 의미 매핑 7개를 사용한다. 기존 성립전예산요구 등록의 매핑·용도와 달라, 과거 5종 승인을 새 등록 승인으로 전용하지 않았다. 각 작업 폴더의 `review.draft.json`에서 confirmed=false와 빈 승인/판독 기록을 유지했다.

[W1·W2 평가용 문안](../tmp/remaining-20260913/workflow-drafts.md)을 제시하고 확인을 요청했다. W1은 기능 시험 계획, W2는 가상교육지원청-200의 시스템 제출용 내부결재이며 가상 회신 기한은 **2026. 10. 8.**이다. 이 문안의 HWPX 생성은 아직 하지 않았다.

확인 대기의 근거는 [hwpx SKILL.md](../.claude/skills/hwpx/SKILL.md)가 연결한 [업무 절차](../.claude/skills/hwpx/references/workflow.md)의 **“확인받은 입력과 초안의 해시를 기록한 뒤 build한다”**, **“사용자가 실제 양식·매핑·용도·현재 해시를 확인한 기록을 받은 뒤에만 제출한다”**이다. 프로젝트 CLAUDE.md에도 초안 확인 기록과 승인 입력 해시 없이 build하지 않는다고 명시되어 있다. 제시한 문안 확인과 등록 검토가 끝나면 이어서 실행할 수 있다.

전달 처리 자체는 과거부터 `SYNTHETIC_TEST_NOT_USER`로 명시된 소프트웨어 시험 입력 두 건을 **변경 없이 재사용**하여 확인했다. 새 승인 입력을 생성하지 않았다.

| 전달 시험 | Claude CLI | 현재 Codex Desktop |
|---|---|---|
| build 및 전체 validate | 두 문서 통과 | 두 문서 통과(첫 문서는 앞서 만든 동일 작업을 이어서 검증) |
| 외부 복사 폴더 없음 | deliver exit 1, 로컬 검토본 유지 | 동일 |
| 폴더 복구 후 복사만 재시도 | exit 0, 로컬/외부 HWPX와 최종 보고서 대조 통과 | 동일 |
| 외부 기존 HWPX 충돌 | 두 번 exit 1, 기존 파일 유지 | 동일 |
| 세 번째 호출 | exit 2, 2회 실패 한도 안내 | 동일 |
| 보존 검사 | 문서 해시·manifest·검증 history 불변, sent=false | 동일 |

이 결과는 전달 실패 처리의 실제 실행 근거다. **새 등록 → 사람의 W1·W2 문안 확인 → 생성 → 최종 검토 전체 인수를 완료한 결과가 아니다.**

보존한 실패와 차이:

- 첫 전달 시험 스크립트가 build 후 별도 validate를 빠뜨려 전달이 정상 거절됐다. 스크립트 v1과 실패 JSON을 보존하고 같은 작업을 이어서 수정했다. 작업번호/실패 횟수 초기화는 하지 않았다.
- 수정한 시험을 Codex workspace-write CLI에서 실행했을 때 한글 단계가 90초 시간 초과여서 전달 분기에 도달하지 못했다. 같은 파일·Python·검사 명령을 현재 Desktop 세션에서 직접 실행하면 약 7초에 열렸다. 이후 현재 Desktop에서 전체 검증과 전달 시험을 완료했다. 실행 환경의 차이를 관측했지만 원인을 확정하거나 CLI 문제를 해결했다고 주장하지 않는다.
- Claude 등록 시험 호스트는 보고서 저장 직전에 360초 제한에 걸렸으나, 세 명령과 검토 자료 8단계 완료는 반환된 도구 출력·registration.json·PDF/PNG로 확인했다. 호스트 시간 초과는 그대로 보존했다.
- Codex CLI 등록 준비는 COM 직렬 실행을 위해 registration.json 생성 전에 중단했다. 이후 현재 Desktop 도구로 실행했으며 독립 CLI 등록 완료로 표기하지 않는다.
- 마지막 확인 때 잔존 Hwp.exe는 없었다.

## 렌더 오탐 수정

이전 검사는 논리 텍스트에 없는 `◯`를 발견하면 원본 상태와 관계없이 실패했다. 이제 `--reference`도 PDF로 내보내 문자별 개수를 비교한다.

- 원본에도 렌더되고 개수가 증가하지 않은 문자는 `warnings`와 `checks.object_residue.inherited`에 남긴다.
- 새 문자, 원본보다 증가한 문자, 레퍼런스 없는 의심 문자는 계속 실패한다. 원본 PDF 추출 실패는 검사 불가다.
- 쪽수·앵커·역순·순서 검사는 유지했다. 개수 일치가 위치·의미 보존을 보증하지 않는다는 경고를 남긴다.
- 회귀시험 8개를 추가했고 전체 103개가 통과했다.
- 기존 7쪽 HWP → HWPX 사본은 원본/결과 `◯` 각 1개, 앵커 발견율 1.0, 순서 비율 0.938, PASS + 원본 기인 경고였다. 7쪽 모두 원본 PDF와 72dpi 픽셀이 같았다. 5쪽 PNG도 직접 확인했다.

## 정식 패키지

GitHub API를 다시 조회한 결과 업스트림 tree `cb5f25b6557b47b0339398d3b5d45a57bdcb4b28`의 license=null, 라이선스 파일 없음, [라이선스 요청 이슈 #4](https://github.com/Canine89/hwpxskill/issues/4)는 open/댓글 0이었다. 공개 저장소라는 사실로 재배포 허가를 만들지 않았다.

현재 해시의 패키지 게이트는 exit 2, release_ready=false다. 권리 미확인 70건·개인정보 검토 미확인 70건·의존성 라이선스 조건 미확인 8건을 유지했다. Hwp_doc 자체 라이선스, 업스트림 재배포 허가, PyMuPDF의 AGPL/상용 적용 경로에 대한 기존 결정을 요청했으며 응답은 아직 없다. 자세한 조건은 기존 [라이선스 원문 확인 보고서](배포-라이선스-원문확인-2026-09-13.md)에 있다.

따라서 **정식 패키지 생성·설치·업데이트·제거 시험은 미실행**이다. 개발 사본의 이전 설치 경로 변경 시험을 정식 패키지 수명주기 시험으로 바꾸지 않았다. 권리자에게 메시지를 보내거나 외부에 게시하지 않았다.
