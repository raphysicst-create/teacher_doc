# 구현 세션과 평가 설계 합의

- 합의일: 2026. 9. 13.
- 설계 세션: 01a094c1-d1d6-7251-8eef-39a5652871c4
- 상대 세션 제목: **플러그인 보급 개선계획 구현**
- 상대 세션 ID: 01a09645-dd81-72c0-8065-fe87ee1807ee
- 채널: Codex 세션 간 send_message_to_thread와 상대의 실제 회신
- 원 요청: “전체 과정에 대한 개별 evals 합의해서 만들어줘. 평가는 또 다른 세션이 할꺼야”

상대 세션은 실제 회신에서 “평가 설계 제안에 동의합니다. evals/plugin_distribution/은 귀 세션 전용으로 두겠습니다.”라고 확인했고, 추가 회신에서 “32개 사례 구조와 scorer/평가자 분리에도 동의합니다.”라고 명시했다. 아래는 두 회신의 합의 내용 요약이며 평가 결과나 사람 문서 승인이 아니다. 원문은 위 세션 대화에 남아 있다.

## 합의한 기준

1. 개선 계획을 정답으로 삼고 미완성 구현을 정답으로 고정하지 않는다.
2. 32개 상위 사례에서 앱·양식·실패 variant는 각각 결과/증거를 갖는다. 한 행의 pass로 미실행 행을 채우지 않는다.
3. 기존 5종 전부 실제 생성·필수 검증·서식 보존을 확인한다. 이관과 E2E에서 증거를 연결할 수 있지만 별도 양식의 성공으로 대체하지 않는다.
4. 기안문 8건 계보는 실제 파일 대조가 필요하다. 자료 미확보는 pending/blocked다.
5. W2 네 제출 분기와 근거 partial/connection_error를 독립 시험한다. 조건·예외·최신판 미확인을 확정 의무로 바꾸지 않는다.
6. 승인 후 원문·첨부·양식/매핑·review 변경, 경로/junction 이탈, 내부 실패/exit 0/손상 상태, COM/필수 렌더 불가, 재시도 한도, 제목 굵기·배치를 포함한다.
7. 모의 승인·모의 COM·CLI 실행은 실제 앱/사람 증거가 아니다. 두 앱은 각각 순차 평가하며 동시 실행을 제외한다.
8. 기대된 안전한 실패 보고는 행동 pass일 수 있지만 완성 문서 수와 분리한다. 환경 진단 pass와 E2E blocked가 공존할 수 있다.
9. 미실행·미구현은 pending, 전제 부재는 blocked, 실행한 명세 위반은 fail, 필수 증거 충족은 pass. 미구현을 범위에서 삭제하거나 N/A로 처리하지 않는다. 성공 주장 자체가 거짓이면 fail이다.
10. 대상 HEAD뿐 아니라 허용 파일 목록·각 파일 해시·git diff·미추적 목록을 고정한다. 대상/기준/fixture 변경은 stale로 처리하고 결과에 맞춰 기준을 재설정하지 않는다.
11. 집계기는 원시 증거 해시·필수 항목을 검사할 뿐 시각 품질·실제 사람/앱 실행의 진위를 보증하지 않는다. 별도 평가자의 원증거 대조와 확인 기록이 필요하다.
12. 성능은 실측과 동일성 유지가 기준이다. 임의 초/배율 목표를 추가하지 않는다.

## 역할·변경 범위

설계 세션은 evals/plugin_distribution/만 작성하고 집계기 자체 검사를 수행한다. 기존 workflow_5·36회 인수·실무 review_log·제품 파일은 수정하지 않는다. 상대 구현 세션은 이 디렉터리와 평가 산출물을 수정하지 않는다.

초기 합의 시 제품 구현은 중단 상태였으나, 최종 검토 회신에서 상대는 이후 사용자의 별도 “구현 시작해” 지시로 제품 구현을 재개했다고 확인했다. 이 evals 합의는 구현 재개 승인으로 해석하지 않는다. 실제 평가는 사용자가 지정할 다른 세션이 수행한다. 새 평가 세션 생성이나 실제 앱·COM·교사 평가를 이 설계 작업에서 시작하지 않는다.

## 작성 파일에 대한 최종 검토

상대는 CONTRACT/AGREEMENT/OPERATOR/FIXTURES와 evaluate.py를 읽기 전용으로 검토하고 “전체 역할 분리·미실행 variant 보존·stale·fixture 결합 구조는 합의와 일치합니다.”라고 확인했다. 실행 환경 필드 누락과 outcomes의 일부 무효 증거 참조도 통과를 막도록 보완하라는 두 의견을 받았고 집계기와 자체시험에 반영했다. 실제 제품 평가는 수행하지 않았다.

이후 상대의 최종 구현 인계를 받아 CONTRACT.md의 CLI·스키마·종료코드·미검증 범위를 갱신했다. 상대가 보고한 개발 시험 69개 통과는 독립 평가 실적이 아니며, 평가자는 초기 구현의 미완료 목록 대신 현재 후보를 새로 동결한다. 사례와 합격 기준은 낮추지 않았다.

추가 인계의 개발 시험 89개, 배포 후보 70파일, runtime 변경 시 미확인/전체 재검증, --review-draft 및 5종 등록 초안도 CONTRACT.md에 반영했다. 모두 구현자의 보고이며 실제 평가·사람 승인으로 합산하지 않는다. 평가가 시작된 뒤에는 이처럼 계약 파일을 갱신하면 기존 run이 stale가 되므로, 평가자는 안정된 후보와 계약을 함께 동결한다.
